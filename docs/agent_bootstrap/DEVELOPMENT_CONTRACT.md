# PMW Generative Sandbox v1
## 完整机制语言、AI 技能创造与长期自主开发契约

**项目基线：** `pmw-engine-v2-feature-alpha-v02-seventh-night`

**项目预算上限：** ¥2,000

**模型分工：** GPT 负责规划、机制审查和关键问题；DeepSeek 负责主要编码实现；DS V4 Flash 系列承担游戏内技能生成。

**首要任务：** 在现有 PMW Engine、Gameplay 与 Alpha 基础上，恢复完整的机制表达空间，并将其交给受约束的 AI 技能生成器使用。

**开发原则：** Engine-first、真实执行、可复现、逐阶段验收、保持可玩版本。

---

# 第一章：不可改变的设计原则

## 1. 三个系统必须明确分离

PMW 具有三个不同层次：

**World：世界规律**

定义世界具有什么状态、如何随时间变化、事件如何产生，以及状态之间有哪些关系。

**Skill：能力与机制干预**

通过受类型约束的 Operator 修改世界状态、动力学、过程、实体状态及关系。

**Agent / Player：决策者**

观察当前可获得的信息，选择行动、创造技能、使用技能并承担世界变化的后果。

必须保持以下边界：

- 世界规律不应依赖某张特定技能卡才能运行。
- 技能不应通过专门的地图名称判断来实现效果。
- 玩家和 NPC 使用同一套权威状态与执行机制。
- AI 生成器不能直接修改权威 WorldState。
- 自然语言描述不能代替实际执行语义。
- 模型不能生成任意 Python、JavaScript 或其他可执行源码来绕过技能语言。

**验收标准：同一个合法 SkillSpec 必须能够在不同的、拥有兼容状态与规则的世界中使用。**

## 2. 高自由度不等于无限制

允许 AI 自由组合合法机制，但禁止：

- 越权修改隐藏世界状态。
- 任意创建资源或无限循环生产资源。
- 生成未授权的实体、Operator 或效果。
- 执行无限递归事件链。
- 绕过正式行动成本和 World Tick。
- 直接修改任务完成、死亡判定或胜利状态。
- 通过动态执行代码扩展技能权限。

限制应主要来自类型、材料能力、效果预算、作用域、时间成本和执行资源预算，而不是预先列出的少量技能模板。

# 第二章：完整世界状态类型系统

## 3. 六类基础世界状态

所有状态采用统一的类型化目录。

### Field

具有连续数值的局部场量。

例如：

- 温度。
- 湿度。
- 电荷。
- Mana 浓度。
- 光照。
- 毒雾浓度。
- 生物量密度。
- 气压。

每个 Field 声明：

- 稳定 ID。
- 数据类型与单位。
- 数值范围。
- 所属 Entity 或 Area。
- 当前值。
- 动力学定义。
- 可观察性规则。
- 可被何种 Operator 修改。

不允许技能仅凭任意字符串创建未经注册的 Field。

### Stock

具有库存与数量语义的资源。

例如：

- 水。
- 木材。
- 矿物。
- 燃料。
- 养分。
- 孢芽。
- 可用能量储备。

Stock 必须区分数量、容量、来源及合法转移。

Stock 可以没有自然恢复吸引子；恢复可以由 Law、Process 或事件驱动。

不能强制所有资源自动再生。

### Process

具有状态、进度、速率、输入、输出和生命周期的过程。

例如：

- 燃烧。
- 生长。
- 结晶。
- 充能。
- 腐蚀。
- 资源转化。
- 扩散。

Process 可以消耗 Stock、产生 Stock、驱动 Field 或触发事件。

允许使用通用过程定义构建新的合法过程实例，而不是只能启动若干写死名称的过程。

### Relation

连接两个或更多实体、对象或 Area 的类型化关系。

例如：

- 供能。
- 导通。
- 相邻。
- 附着。
- 依赖。
- 控制。
- 通行。
- 资源传输。

Relation 必须声明端点类型、方向性、状态、约束和生命周期。

修改 Relation 可以改变世界交互结构，但不能直接绕过任务胜利条件。

### Discrete

有限状态集合以及合法状态转换。

例如：

- 天气。
- 生态阶段。
- 设备运行状态。
- 门的开闭。
- 生物形态。
- 过程阶段。

Discrete 具有明确的转换规则、条件与事件。

技能通常应通过改变底层条件触发转换，而不是直接宣告某项世界事件已经发生。

### Derived

由其他状态计算出的只读派生量。

例如：

- 导电风险。
- 能见度。
- 生态稳定度。
- 设备可用性。
- 区域危险程度。

Derived 必须由无副作用表达式计算。

技能不能直接写入 Derived，只能修改其依赖状态。

## 4. 世界目录与实例分离

必须区分：

**World Catalog：** 声明有哪些状态类型、Operator、Law、Trait、Process 模板和关系类型。

**World Instance：** 存储某局游戏中真实的 Area、Actor、Object、状态数值和活跃过程。

AI 可以通过合法机制修改实例。

本阶段不允许技能生成器任意修改类型系统本身。

未来可以另设 World Generator 负责生成新的合法目录与世界规律，但不与当前 Skill Generator 混为一体。

## 5. Area 是局部机制的基本单位

每个 Area 拥有：

- 自己的 Field 与 Stock。
- 自己的动力学参数。
- 本地 Law。
- 当前 Process。
- Actor 与 Object。
- 离散状态。
- 与其他区域的 Relation。

所有 Area 随统一 World Tick 演化。

区域之间不发生默认的自动扩散。跨区域影响必须由明确的 Law、Process 或 Relation 实现。

离开 Area 不会停止其演化，也不能导致其状态无条件重置。

# 第三章：动力学语义

## 6. 完整动力学

基础模型：

`Dynamics = (target, rate, curve)`

必须至少支持：

- 无恢复。
- 一阶线性吸引子恢复。
- 距离平方型非线性恢复。

实现时需对每条曲线规定精确、确定性的数值更新公式。

线性模式可采用：

`x_next = x + rate * (target - x)`

距离平方型模式可采用：

`x_next = x + rate * (target - x) * abs(target - x)`

上述公式是默认规范化语义；应明确变量尺度与 rate 的允许范围，保证更新有界、可复现，不因不合理参数产生数值发散。

每次更新遵守状态定义的范围。

## 7. 四种不同的动力学干预

必须严格区分：

1. **Impulse：** 直接修改当前值。
2. **Drive / Source：** 在持续时间内注入或移除状态量。
3. **Attractor Modifier：** 修改恢复目标。
4. **Dynamics Modifier：** 修改恢复速率、曲线或其参数。

这些干预不能被简化成同一种 `delta`。

例如，将生物量增加 0.2，与将生物量吸引子提高 0.2，是两种不同的机制，应在后续多个 Tick 中表现出不同的结果。

## 8. 多重修改共存

所有持续修改都必须具有：

- 唯一 ID。
- 来源。
- 目标。
- 开始 Tick。
- 到期条件。
- 叠加语义。
- 生命周期状态。

多个技能可以同时修改同一个动力学参数。

默认采用可组合且可逆的修改层，不直接覆盖基础参数。

例如：

- 有效吸引子由基础目标与有效目标修正组合得到。
- 有效恢复率由基础恢复率与合法倍率修正组合得到。
- 曲线修改采用明确的优先级或冲突拒绝规则，不允许结果取决于容器遍历顺序。

一个修改到期，只移除自己的贡献，不得覆盖其他修改或改写基础值。

# 第四章：七类基础 Operator

## 9. Operator 契约

所有技能必须通过统一 Operator 执行接口生效。

至少支持：

### 9.1 impulse

一次性修改合法目标的当前数值或状态量。

支持范围：

- Field 当前值。
- Stock 数量。
- Actor 的合法属性、HP、Mana 或状态效果。

必须有类型与数值界限。

### 9.2 drive/source

在指定时间内持续向目标注入、转移或移除状态量。

必须声明：

- 目标。
- 速率。
- 持续期。
- 合法来源或生成规则。
- 是否消耗资源。
- 作用范围。

涉及资源转移时必须符合守恒或显式来源声明。

### 9.3 attractor_modifier

修改 Field 或允许自然恢复的 Stock 的吸引子目标。

支持：

- 固定偏移。
- 合法倍率。
- 有界持续时间。
- 可追踪来源。

### 9.4 dynamics_modifier

修改动力学恢复率、曲线或已声明的参数。

必须保证数值稳定性，并支持到期恢复。

### 9.5 process_start

创建一个通过类型验证的 Process 实例。

允许通过受约束的过程配置定义：

- 输入。
- 输出。
- 执行速率。
- 终止条件。
- 持续期。
- 必要环境条件。

不允许生成任意执行代码。

### 9.6 process_modify

对活跃 Process 施加合法修改：

- 速率。
- 进度。
- 允许修改的参数。
- 暂停与恢复。
- 受限的剩余持续时间修改。

不能任意修改其他 Process 的内部实现。

### 9.7 relation_modifier

创建、终止或调整具有合法类型的 Relation。

必须验证：

- 端点存在且类型正确。
- 作用范围与材料权限足够。
- 关系变化符合拓扑约束。
- 不产生非法世界状态。
- 临时关系能够正确到期。

直接创建 `game_won`、`boss_dead` 之类的任务控制关系不属于普通技能权限。

## 10. 不允许退化为硬编码模板

新增一种技能，不应该需要：

- 修改 Session 中的技能名称分支。
- 为技能添加专属 Python 函数。
- 在 UI 中判断技能名称并执行效果。
- 修改某个特定 Area 的关卡代码。

如果技能所需语义已由 Operator 支持，那么它必须能够仅通过数据化 SkillSpec 表达。

若确实遇到表达能力不足的技能，应记录为语言缺口，而不是添加技能专属特判。

# 第五章：Skill IR

## 11. 统一技能中间表示

Skill IR 至少包含：

| 字段组 | 内容 |
|---|---|
| Identity | 技能 ID、版本、名称、描述 |
| Origin | 生成模型、生成上下文、来源材料 |
| Capability | 材料 Trait、允许的 Operator 与权限 |
| Targeting | 目标类型、选择器、作用域 |
| Costs | Mana、材料、时间、其他资源 |
| Triggers | 主动使用、Tick、事件、条件转换 |
| Conditions | 类型化逻辑表达式 |
| Effects | 有序或显式依赖的 Operator 序列 |
| Lifecycle | 持续期、触发次数、冷却、到期行为 |
| Limits | 目标数量、执行预算、递归限制 |
| Display | 玩家可读说明和效果预览 |

允许一个技能包含多个触发入口及多个 Operator。

不能强制所有技能都采用 Core × Modifier 的固定结构。

## 12. 条件语言

必须支持基本的类型化条件：

- 比较。
- 区间判断。
- Trait 存在判断。
- Discrete 状态判断。
- Process 状态判断。
- Relation 存在判断。
- 多条件 AND / OR / NOT。
- 事件参数匹配。
- 有界的持续时间或连续满足条件判断。

所有条件必须无副作用。

目标查询和条件复杂度必须受预算约束。

不得允许 SkillSpec 注入任意表达式执行器代码。

## 13. 目标选择器

至少支持：

- Self。
- Selected Actor。
- Current Area。
- Selected Object。
- Matching Actors。
- Matching Objects。
- Matching Processes。
- Matching Relations。

集合选择必须声明允许的作用域、最大目标数量和 Trait / Type 过滤条件。

跨区域目标必须获得明确权限，不能仅通过任意 Area ID 绕过范围约束。

## 14. Trigger 与事件

至少支持：

- `on_use`
- `on_tick`
- `on_event`
- `on_expire`
- 条件成立或退出时的状态转换事件

事件包含：

- 类型。
- 来源。
- Tick。
- 作用 Area 或 Entity。
- 合法的事件参数。
- 因果父事件 ID。

同一事件不应因为多个系统重复扫描而触发同一技能多次。

应明确事件队列顺序、同 Tick 内触发语义和递归预算。

## 15. 技能生命周期

所有持续效果遵守统一生命周期规则。

必须明确：

- 创建与生效时间。
- 到期时间。
- 同类效果叠加方式。
- 冷却。
- 最大触发次数。
- 解除与取消。
- 来源消失时的处理。

主动技能、被动技能和环境技能应复用同一套生命周期与事件机制。

# 第六章：确定性执行与安全契约

## 16. 权威状态与事务

SkillSpec 只能通过正式 Action / Effect 入口修改权威世界。

一次技能使用必须完成：

1. 合法行动检查。
2. 技能装备与权限检查。
3. 目标与材料检查。
4. 资源与时间成本检查。
5. 在事务状态中结算效果。
6. 生成事件并结算同步后果。
7. 推进所需 World Tick。
8. 完整成功后提交。

失败时不能留下：

- 扣除了一半的材料。
- 已写入但未结算的世界状态。
- 未清理的 Scheduler 事件。
- 错误的资源生产。
- 已经触发却没有来源的被动效果。

AI API 调用不能出现在权威游戏事务内部。

## 17. World Tick

必须有唯一、文档化、经过测试的 Tick 顺序。

建议以现有引擎正式顺序为基础，明确以下阶段：

1. 已提交行动带来的即时效果。
2. 有效 Dynamics 参数计算。
3. 所有 Area 的自然演化。
4. 活跃 Drive / Source / Process 结算。
5. Law 和离散状态转换评估。
6. 事件产生及有界分发。
7. 被动效果与状态生命周期结算。
8. Scheduler 到期事件。
9. 世界 Tick 提交及终局判定。

P0 必须核对当前 Engine 的真实语义，再冻结唯一实现顺序。

不得因为引入 Skill IR 而创建第二套 Tick 系统。

## 18. Process 结算

Process 的资源输入与输出应在同一原子步骤内结算。

当输入资源不足时，采用明确的失败、暂停或按比例缩放规则，并保持过程的输入输出比例一致。

不得允许负库存、重复提交或无来源的无限资源增殖。

允许 World Law 显式定义开放系统来源，但技能不能通过省略成本自动取得无限能源或资源。

## 19. 计算资源限制

技能必须受到可配置的执行预算约束：

- 单次效果数量。
- 单次事件触发深度。
- 单个 Tick 的触发总数。
- 集合查询最大目标数量。
- 活跃 Process 数量。
- 活跃持续效果数量。
- 单次结算的 CPU / 时间预算。

参数由 P1 实测决定，先使用保守默认值。

超出预算时必须产生可解释的失败或安全终止，不能无限递归或破坏游戏状态。

# 第七章：AI 技能生成契约

## 20. DeepSeek 的角色

DS V4 Flash 系列作为 Skill Designer。

实际接入时核对供应商当前有效模型 ID、接口能力、结构化输出支持和计费方式。

不要在代码里假设某个未经确认的 API 名称永远有效。

生成器负责：

- 理解材料 Trait。
- 查看完整 Skill IR 语言。
- 选择合法机制。
- 组合 Operator。
- 设计条件、触发器、持续期与成本。
- 生成技能名称和可读说明。

生成器不负责：

- 直接执行效果。
- 修改 WorldState。
- 决定编译器是否放行。
- 绕过材料权限。
- 修改引擎代码。
- 读取玩家无权获知的任务答案。

## 21. 模型必须看到完整机制语言

向生成器提供完整的可用机制 Catalog。

不能只告诉它：

- 允许加湿度。
- 允许加电荷。
- 允许造成伤害。
- 允许增加护盾。

必须暴露六种状态类型、七类 Operator、条件表达式、Process 能力、Relation 语义、动力学、触发器和生命周期。

模型只能使用经验证可用的机制，却应拥有自由组合这些机制的空间。

## 22. 生成输入

至少包含：

- 材料及其 Trait。
- 当前可用的 Operator Catalog。
- 玩家已获得的能力。
- 玩家已知的世界规律。
- 合法的作用范围。
- 能力预算。
- 生成复杂度等级。
- 现有技能的结构摘要，用于减少重复。

不得输入未经授权的完整隐藏世界状态。

## 23. 生成与验证流水线

严格执行：

**Context → Generate → Parse → Normalize → Type Check → Capability Check → Budget Check → Compile → Sandbox Test → Register**

任何一步失败，都不能将技能注册为可使用技能。

允许模型在收到结构化错误反馈后修复候选，但必须限制重试次数。

不能通过无限重试消耗 API 额度。

## 24. 两种生成模式

### 离线生成

批量生成候选技能，使用统一验证器筛选。

用于：

- 机制表达空间测试。
- 技能多样性评价。
- 预生成随机技能池。
- 自动化试玩。
- 无网络运行时的备用技能。

### 局内生成

玩家在游戏中消耗材料领悟技能。

流程：

1. 玩家合法提交材料。
2. 生成器产生有限个候选 SkillSpec。
3. 验证候选。
4. 玩家查看效果与成本。
5. 玩家选择并正式制作或注册。
6. 游戏保存已验证 SkillSpec。

生成失败时，提供明确重试或使用预验证候选的方案。

不能因为 API 超时直接损失已提交的材料。

## 25. 存档与复现

生成完成的技能必须具有：

- 标准化 IR。
- 版本。
- 内容哈希。
- 来源记录。
- 所使用的 Catalog 版本。

存档保存已经编译和验证的技能定义。

# 第九章：长期 Agent 自主开发协议

## 26. 模型分工

**GPT：**

- 架构与机制决策。
- 高风险修改审查。
- 阶段验收。
- 复杂缺陷诊断。
- 游戏性评估。
- 下一轮任务选择。

**DeepSeek Coding Agent：**

- 实现。
- 常规测试。
- 局部重构。
- UI。
- 内容和机制适配。
- 缺陷修复。

**DS Flash Skill Designer：**

- 生成结构化技能候选。
- 根据验证错误有限修复候选。
- 不参与权威世界结算。

**Automated QA：**

- 运行现有测试。
- 创建反例。
- 检查回归。
- 验证技能执行安全。
- 记录可复现问题。

**Playtest Agent：**

- 通过正常游戏入口游玩。
- 不依赖隐藏答案。
- 报告策略、困惑、无效行动及玩法问题。

## 27. 每轮自主开发流程

1. 读取当前代码、最新测试和问题池。
2. 选择一个影响最大的具体目标。
3. 记录成功标准与回归风险。
4. 分配实现任务。
5. 执行代码修改。
6. 运行单元、集成与回归测试。
7. 执行相关的真实机制或游戏测试。
8. 由独立审查判定接受、修复或回滚。
9. 保存工作检查点。
10. 更新项目状态与下一轮优先级。

每轮不应同时进行多个不可归因的巨大重构。

对于相互独立的模块，允许并行开发，但必须分开工作区或明确文件所有权。

## 28. 失败升级

同一缺陷连续两轮修复失败：

- 停止重复尝试。
- 交给 GPT 重新分析根因。
- 检查是否为设计契约或接口假设错误。

连续三轮没有产生有效改进：

- 暂停当前方向。
- 审查设计与测试有效性。
- 必要时回滚到最近稳定版本。
- 重新选择任务。

禁止用放宽测试、删除断言或伪造游戏状态的方式解决问题。

## 29. 游戏质量优先

不能只以功能数、测试数量和代码量评价进展。

必须长期追踪：

- 技能机制的有效多样性。
- 构筑之间的策略差异。
- 玩家行动选择的实际价值。
- 长期世界变化出现的频率。
- 环境机制与战斗互动的深度。
- 玩家能否理解世界反馈。
- 是否存在显著占优的单一策略。
- 是否存在大量无意义重复操作。
- 游戏失败是否可理解。
- 是否能够稳定完成整局游戏。

自动试玩报告必须影响下一轮开发优先级。

# 第十二章：最高优先级验收原则

整个开发过程中，以下五条不可妥协。

**一、机制表达完整。**

不得再把高自由度系统压缩为四个材料 Core、三个 Modifier 和几种固定技能模板。

**二、世界执行真实。**

技能作用必须进入正式 PMW WorldState，并由真正的 Dynamics、Process、Law、Relation 与事件机制产生后果。

**三、AI 创造自由。**

生成器能够组合完整的合法机制空间，而不是只能从几个预设效果中选择。

**四、游戏结果可验证。**

随机技能生成之后必须可保存、可执行、可复现、可解释，且不能依赖生成器在执行时重新解释语义。

**五、长期开发始终服务于游戏性。**

引擎能力不是最终目的。最终目的是让玩家利用自己创造的能力，发现、改变并驾驭一个持续演化的世界。

**执行起点：P0 能力审计。通过能力审计明确差距后，按 P1 → P2 → P3 → P4 → P5 的顺序推进，不需要反复请求普通工程决策的确认，但必须遵守阶段 Gate、冻结边界、预算上限和真实验证要求。**
